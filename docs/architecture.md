# 最長老 設計書（検索・インデックス基盤）

- ステータス: ドラフト v0.1
- 最終更新: 2026-11-26

---

## 1. 概要

### 1.1 目的
「最長老」は、社内情報について何でも答えられるチャットボットである。
社内情報の大半は SharePoint Online（以下 SPO）にあり、閲覧できる範囲は人によって異なる。
そのため **各利用者の委任権限の範囲内で検索・回答する** ことを最重要の要件とする。

### 1.2 対象データ

| データソース | 内容 | 閲覧制御 | 索引化の方針 |
|---|---|---|---|
| SPO | 部門文書、プロジェクト文書など | SPO の権限（人によって異なる） | 検索をきっかけに非同期で索引化し、使われるほど充実させる |
| 社内 Web | 規程など全社向けの情報 | 2区分（正社員のみ ／ 派遣・委託社員まで） | 事前に全件を索引化する |

### 1.3 設計原則

1. **委任権限のみで構成する**。アプリ権限は使わない（5章）。
2. **権限の正解は常に情報源側にある**。自前の索引は候補を出すだけで、回答に使う前に必ず閲覧権限を確認する。
3. **フェイルクローズ**。区分や公開範囲が判定できない場合は、閲覧範囲が狭い側として扱う。
4. **本文は全社で1つだけ持ち、各人には参照だけを持たせる**。各人ごとに本文をコピーした索引は作らない。
5. **絞り込みは検索時に行う**。閲覧してよいかの判断を LLM にさせない。
6. **派生物にも権限を引き継ぐ**。用語辞書、要約、キャッシュ、学習データも、元の文書の閲覧範囲を引き継ぐ。

## 3. 社内 Web（全社向けデータ）

### 3.1 クロール
- 社内 Web は社内ネットワーク内にあるため、クローラーは **社内ネットワーク内**、または **閉域接続（VPN / ExpressRoute 等）で到達できる環境** で動かす。
- 定期的にクロールし、ETag / Last-Modified / sitemap を使って差分だけを取り込む。
- 規程は改訂日・版数をメタデータとして保持し、回答に「〇年〇月改訂版」と添えられるようにする。

### 3.2 公開範囲（audience）の判定
- 公開範囲は「閲覧できる区分の集合」として持つ。
  - `['employee']`：正社員のみ
  - `['employee', 'contractor']`：派遣・委託社員まで
  - 未判定のものは `['employee']` として扱う（フェイルクローズ）
- 判定は推測せず、**社内 Web サーバーの実際のアクセス制御を正とする**。
  - 推奨：クローラー用に「正社員相当」「派遣委託相当」の2つのサービスアカウントで巡回し、派遣委託相当のアカウントでも取得できた文書だけを `contractor` 可とする。
  - それができない場合は、サーバーのアクセス制御設定（ディレクトリ単位など）の一覧を入手して判定基準にする。
- 再クロールのたびに判定し直し、公開範囲が変わった文書はチャンクと派生物（9.2）をすべて付け替える。

### 3.3 規程の構造化
- 章・条・項の単位でチャンク化し、条番号を保持する。
- 「第12条の規定にかかわらず」のような条文間の参照をリンクとして保持し、検索時に関連する条文もあわせて取り出す。
- 参照先の条文の公開範囲が利用者の区分で閲覧できない場合は、その参照を辿らない。

### 3.4 SPO との重複
- 規程の PDF などが SPO にコピーされている場合は、ハッシュや類似度で同じ文書と判定し、**社内 Web 側を正本** として扱う（古い版のコピーを引用しないため）。

### 3.5 代替案：Graph コネクタ
社内 Web は Graph コネクタ（Copilot コネクタ）でページごとに ACL を付けて Microsoft Search に取り込むこともできる。

| | 自前の索引（採用） | Graph コネクタ |
|---|---|---|
| 権限の制御 | 自前で実装 | M365 が行う |
| 社内用語への対応・チャンク化の工夫 | 自由にできる | 限られる |
| 規程の条単位の構造化 | できる | 難しい |
| データの置き場所 | 自分で選べる | M365 テナント内 |

規程は回答品質の要なので自前の索引を採用する。ただし、データを M365 の外に出せない場合は Graph コネクタを代替案とする。

## 4. SPO（検索をきっかけに作る各人の索引）

### 4.1 考え方
- 本文・チャンク・埋め込みは **文書ごとに1つだけ** 持つ（driveItem の ID と eTag で重複を除く）。
- **各人の索引** の実体は、「この人はこの文書を閲覧できると確認済み」という記録（以下 **確認済みアクセス**、`access_edges` テーブル）と、利用傾向などの個人シグナルである。
- 確認済みアクセスは、利用者本人の Graph Search の結果に出た文書、または本人トークンでの取得に成功した文書についてだけ登録する。
  → 他の人がすでに取り込んだ文書でも、本人が閲覧できると確認できれば本文を共有して使える（漏洩にはならない）。

### 4.2 検索時の処理（同期）
1. Graph Search API（`/search/query`）を委任トークンで呼ぶ。利用を始めた初日から、権限で正しく絞られた結果が得られる。
2. 共有チャンク索引を「本人の確認済みアクセスに含まれる文書」に絞って検索する（キーワードとベクトルの組み合わせ）。
3. 統合後の上位 10〜20 件について、委任トークンで `GET /drives/{d}/items/{i}` を `$batch`（1回あたり最大 20 件）で呼び、閲覧権限を確認する。
   - 403 / 404 → 候補から外し、確認済みアクセスも削除する。
   - eTag が変わっていた → 再取り込みのキューに積む。

### 4.3 非同期での取り込み
- 対象：Graph Search で見つかったが未索引の文書、eTag が変わった文書、先読みの対象。
- 処理：本文取得 → テキスト抽出 → チャンク化 → 文脈付与（8.3）→ 埋め込み → 確認済みアクセスの登録。
- Worker は OBO フローで得た **利用者本人の委任トークン** で動く。

### 4.4 使うほど最適化する仕組み

| 仕組み | 内容 |
|---|---|
| 先読みの範囲拡大 | 検索結果が特定のサイトやフォルダに集中したら、本人トークンでその周辺を先に取り込む（人ごと・日ごとの予算で制限） |
| 鮮度の管理 | よく使われるドライブは `/delta` で差分を追跡する。使われない文書は LRU で消す。確認済みアクセスには有効期限を付ける |
| 並べ替えの個人最適化 | 所属サイト、よく引用する文書、フィードバックを並べ替えの特徴量に使う |
| 文書の品質スコア | よく引用され評価の高い文書のスコアを上げる（人をまたいで使うのは品質スコアだけで、権限は人ごとに確認する） |
| 回答キャッシュ | 引用元のすべてを新しい質問者の権限で確認できた場合にだけ再利用する |
| 用語の学習 | 8.1 を参照 |

### 4.5 除外・特別扱い
- **Restricted Content Discovery（RCD）／ Restricted SharePoint Search の対象サイト**：Graph Search には反映されるが自前の索引には自動では反映されないため、取り込み対象から外す。
- **秘密度ラベルで暗号化された文書**：ラベルごとに「取り込まない」「Graph Search の要約だけ使う」などの方針を決める（未決事項）。

## 5. 権限モデル

### 5.1 委任権限のみで構成する
アプリ権限は使わない。

| 処理 | 使う権限 |
|---|---|
| 検索（Graph Search） | 利用者の委任トークン |
| 回答前の権限確認（`$batch`） | 利用者の委任トークン |
| 非同期での取り込み・先読み | OBO フローで得た利用者の委任トークン（リフレッシュトークンを保管） |
| delta による差分追跡 | 追跡対象を閲覧できる利用者の委任トークン（その人が権限を失ったら、追跡に使う利用者を入れ替える） |

- 必要なスコープ（委任）：`Files.Read.All`、`Sites.Read.All`、`User.Read`、`offline_access`
- 管理者の同意は1回だけ得る。
- リフレッシュトークンは Key Vault などで暗号化して保管する。

### 5.2 委任権限のみにすることによる制約と対策

| 制約 | 対策 |
|---|---|
| 誰も検索していない SPO 文書は索引に入らない | Graph Search で補う。全社向けの情報は社内 Web として事前に索引化する |
| ACL を計算して、他の人に閲覧権限を先回りで付けられない | 権限は1件ずつ本人のトークンで確認する |
| delta 追跡が特定の利用者に依存する | 追跡に使う利用者を入れ替える仕組みを用意する |

将来、特定のサイトだけ先に索引化する必要が出てきた場合は、そのサイトに限って `Sites.Selected` を追加することを検討する。

## 6. 利用者の区分の判定

### 6.1 判定方法
- 社員番号の規則で、正社員かそれ以外かを判定する。
- 社員番号は **Entra ID から委任トークンで取得する**（`GET /me?$select=employeeId`）。クライアントから送られた値は使わない。
- 判定結果はセッションに短い有効期限で保存し、雇用形態の変更も反映されるようにする。

```python
def classify(employee_id: str | None) -> set[str]:
    if employee_id and REGULAR_PATTERN.fullmatch(employee_id):
        return {"employee", "contractor"}   # 正社員：両方の公開範囲を閲覧可
    return {"contractor"}                   # それ以外・不明・空欄：狭い側
```

- 判定は1か所の関数にまとめ、規則（正規表現）は設定ファイルで管理する。
- 正社員の規則に一致したときだけ正社員として扱う。サービスアカウント、管理者アカウント、社員番号が空欄の場合はすべて狭い側にする。
- 想定外の形式の番号はログに記録する。

### 6.2 前提と確認事項
- 人事システムから Entra の `employeeId` に、全員分の社員番号が統一された形式で連携されていること。
- 社内 Web サーバー側の閲覧制御と判定基準が食い違わないこと（3.2 の文書側の判定と組み合わせて両側を揃える）。
- 境界にあたる区分の扱い：契約社員・嘱託・パート、受け入れ・送り出しの出向者、役員、派遣・委託から正社員になった人（番号が変わるか）。

### 6.3 SPO 側
派遣・委託社員にも Entra のアカウントがあるため、SPO については Graph の権限による絞り込みがそのまま効く。追加の対応は不要。

## 7. データモデル（案：PostgreSQL + pgvector）

```sql
-- 文書（社内 Web・SPO 共通）
documents (
  doc_id          uuid primary key,
  source          text check (source in ('corp_web', 'spo')),
  -- 社内 Web
  url             text,
  audience        text[],          -- {'employee'} / {'employee','contractor'}
  revision_date   date,
  -- SPO
  drive_id        text,
  item_id         text,
  site_id         text,
  etag            text,
  sensitivity_label text,
  -- 共通
  title           text,
  path            text,
  content_hash    text,
  canonical_doc_id uuid,           -- 重複している場合の正本
  quality_score   real,
  last_indexed_at timestamptz
);

-- チャンク（全社で共有）
chunks (
  chunk_id     uuid primary key,
  doc_id       uuid references documents,
  level        text check (level in ('doc_summary', 'section', 'chunk')),
  article_no   text,                -- 規程の条番号
  context      text,                -- 付与した文脈（文書名 > 章 > 節、要約1行）
  text         text,
  embedding    vector,
  audience     text[]               -- 社内 Web 文書の audience を複製（検索時の絞り込み用）
);

-- 条文間の参照
chunk_links (from_chunk uuid, to_chunk uuid, kind text);

-- 確認済みアクセス（各人の SPO 索引の実体）
access_edges (
  user_id      text,
  doc_id       uuid,
  verified_at  timestamptz,
  expires_at   timestamptz,
  source       text,                -- 'graph_search' / 'fetch' / 'prefetch'
  primary key (user_id, doc_id)
);

-- 用語辞書
terms (
  term_id        uuid primary key,
  canonical      text,              -- 正式名称
  aliases        text[],            -- 略語・通称
  reading        text,
  definition     text,
  status         text check (status in ('candidate', 'approved')),
  visibility     text check (visibility in ('public', 'scoped')),
  audience       text[],            -- public の場合の公開範囲
  source_doc_ids uuid[]             -- scoped の場合、出典を閲覧できる人だけに使う
);

-- 個人シグナル・質問ログ
user_signals (user_id text, scope_type text, scope_id text,
              hit_count int, click_count int, feedback_score real);
query_log    (query_id uuid, user_id text, user_class text, query text,
              rewritten text, cited_doc_ids uuid[], feedback smallint,
              created_at timestamptz);
```

## 8. 社内用語への対応と検索品質

### 8.1 用語辞書（知識層）

| 作り方 | 内容 |
|---|---|
| 初期データ | 規程の定義条項（「この規程において〇〇とは…」）から LLM で抽出する |
| 自動抽出 | 「XYZ（〇〇システム）」のような括弧書きや、一緒に出てくる語の組から略語の候補を作る |
| 質問ログ | 「A で検索して結果ゼロ → すぐ B で再検索してヒット」という流れから、同義語の候補を作る |
| 人による確認 | 候補（`candidate`）は管理画面で承認されてから使う（`approved`） |

**用語辞書の権限**
- 全員に共有してよい用語（`public`）：社内 Web 由来と、人が承認したものに限る。社内 Web 由来の用語は出典の audience を引き継ぐ。
- SPO 文書由来の用語（`scoped`）：出典の文書 ID を持たせ、その文書を閲覧できる人の質問にだけ展開や定義を使う。極秘プロジェクトのコード名などが辞書を通じて漏れるのを防ぐため。

### 8.2 質問の解釈
1. LLM が用語辞書を参照しながら質問を解釈する（略語を正式名称に置き換える、同義語を展開する）。
2. 検索先ごとにクエリを作る。
   - Graph Search：展開済み KQL（例：`("〇〇申請" OR "△△届出")`）
   - 自前の索引：正規化した文と元の文の両方
3. 根拠が足りないと判断したら追加で検索する（規程から関連条文や様式へ広げるなど）。

### 8.3 索引の工夫
- **キーワード検索（BM25）**：Sudachi などの形態素解析に用語辞書から作ったユーザー辞書を組み込み、社内用語が分解されないようにする。
- **文脈付きチャンク**：埋め込む前に「文書名 > 章 > 節」と要約1行を先頭に付け、本文中の略語の横に正式名称を書き添える。
- **階層化**：文書要約 → 章・条 → チャンクの3段で索引化し、広い質問には要約、細かい質問には条文で答える。
- **統合と並べ替え**：3系統の結果を RRF で統合し、日本語に対応したリランカー（例：bge-reranker-v2-m3、Cohere Rerank の多言語版）で並べ替える。制度や手続きについての質問では規程の重みを上げる。

## 9. 公開範囲の管理（正社員のみ ／ 派遣・委託社員まで）

### 9.1 検索時の絞り込み
- 社内 Web のチャンクは `audience && 利用者の区分` を検索条件に含める。
- 検索結果を LLM に渡してから閲覧可否を判断させる方式は採らない。

### 9.2 派生物の管理

| 派生物 | 対策 |
|---|---|
| 用語辞書 | 出典の公開範囲を引き継ぐ。正社員向け文書だけに出てくる用語は、派遣・委託社員の質問では展開しない |
| 文脈付きチャンク | 付ける文脈は、そのチャンクと同じかより広い公開範囲の文書からだけ取る |
| 条文間の参照 | 利用者が閲覧できない条文への参照は辿らない |
| 文書要約・階層索引 | 公開範囲が異なる文書をまとめて要約しない |
| 回答キャッシュ | キャッシュのキーに利用者の区分を含める。かつ、引用元のすべてが閲覧可能な場合だけ再利用する |
| 学習データ（質問ログ） | 正社員の質問ログから作った用語候補を、全員向けに使わない |

## 10. 運用上の考慮事項

- **流量制限**：SPO にはリソース単位の流量制限があるため、`$batch` で呼び出しをまとめ、テナント全体と人ごとに上限を設ける。429 が返ったら `Retry-After` に従う。
- **データの置き場所**：索引や LLM をクラウドに置く場合、社内 Web・SPO の内容をそこに出してよいかを情報セキュリティ部門に確認する。
- **監査ログ**：質問、引用した文書、利用者の区分を記録する（保存期間は要検討）。
- **トークン管理**：リフレッシュトークンは暗号化して保管し、利用者の退職・無効化時には削除する。

## 11. テストと評価

- **権限の回帰テスト**：派遣・委託社員の役のテストユーザーで、正社員限定の情報が回答・引用・用語展開・関連提案のどこにも出ないことを確認する。CI に組み込む。
- **漏洩の監視**：正社員限定の文書にだけ含まれる、意味のない独自文字列を仕込んだテスト文書を置き、その文字列が派遣・委託社員への出力に一切現れないことを監視する。
- **SPO の権限**：閲覧権限を外したテストユーザーで、確認済みアクセスが残っていても回答に使われないことを確認する。
- **検索品質**：社内の質問と正解文書の評価セットを作り、段階ごとに再現率と回答品質を測る。

## 12. 段階的な実装計画

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 1. MVP | Graph Search と LLM で回答（自前の索引なし）、利用者の区分の判定 | 権限の正しさを確認でき、回答品質の基準値が取れる |
| 2. 社内 Web | クローラー、公開範囲の判定、規程の条単位の構造化、用語辞書の初期データ | 規程に関する質問に出典付きで答えられる。権限の回帰テストが通る |
| 3. SPO 索引 | 共有チャンク索引、確認済みアクセス、`$batch` での権限確認、非同期での取り込み | 段階1より再現率が上がる |
| 4. 検索品質 | 文脈付きチャンク、キーワードとベクトルの組み合わせ検索、リランカー、質問の解釈 | 評価セットのスコアが上がる |
| 5. 学習ループ | 先読みの範囲拡大、delta 追跡、質問ログからの用語候補、並べ替えの個人最適化、回答キャッシュ | 利用が増えるほどスコアが上がる |
| 6. 拡張（必要に応じて） | エンティティとその関係（ナレッジグラフ）、`Sites.Selected` の部分導入 | ─ |

## 13. 未決事項

1. 規模：利用者数、SPO 全体の文書数・容量
2. 実行基盤（社内 / Azure などのクラウド）と LLM、データを置く場所の可否
3. 社内 Web の認証方式（統合 Windows 認証 / SSO / IP 制限のみ）と、クローラー用サービスアカウントの払い出し
4. Entra の `employeeId` の連携状況と、社員番号の規則の正式な定義
5. 境界にあたる区分（契約社員・嘱託・パート、出向者、役員、雇用形態の変更）の扱い
6. 秘密度ラベル付き文書の取り扱い方針
7. M365 Copilot ライセンスの有無（Copilot Retrieval API を比較対象にするか）
8. 監査ログの保存期間と、質問ログを学習に使うことについての社内規定上の可否
